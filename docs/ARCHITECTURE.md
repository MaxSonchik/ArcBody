# ArcBody — архитектура

## 1. Место в системе

ArcBody — телесный аналог сервиса распознавания лиц, а не его замена.
Идентичность человека по лицу остаётся там, где уже живёт; ArcBody хранит
непрозрачный `external_face_id` и умеет только положить его рядом с профилем
тела.

```
                    ┌──────────────────────┐
   фото ───────────▶│   ArcFace (внешний)  │──▶ face_id
                    └──────────────────────┘        │
                                                    │ person_id / face_id
                    ┌──────────────────────┐        │
   фото ───────────▶│       ArcBody        │◀───────┘
                    │  тело: вектор + обмеры│
                    └───────────┬──────────┘
                                │ промпт + control-карты + обмеры
                                ▼
                    ┌──────────────────────┐
                    │  GenAI-провайдер     │
                    └───────────┬──────────┘
                                │ сгенерированное изображение
                                ▼
                    ┌──────────────────────┐
                    │ ArcBody /check-      │──▶ similarity + дельты пропорций
                    │ generation           │
                    └──────────────────────┘
```

Последняя стрелка — смысл сервиса, а не довесок: генерация проверяется тем же
способом, что и вторая фотография — эмбеддингом и разностью пропорций.

## 2. Конвейер обработки

```
изображение
   │
   ├─▶ perception ──────────▶ PersonObservation
   │     детекция, поза,        bbox, 17 ключевых точек, маска, ракурс
   │     сегментация
   │
   ├─▶ quality ─────────────▶ QualityReport
   │     8 именованных гейтов   балл + подсказки «что переснять»
   │
   ├─▶ measure ─────────────▶ BodyMeasurements
   │     геометрия силуэта      пропорции → (× рост) → сантиметры + интервалы
   │
   ├─▶ embed ───────────────▶ 256-мерный вектор + пропорции по мнению сети
   │     кроп 128×256 (RGB+маска)
   │
   └─▶ genai ───────────────▶ промпт, негативный промпт, 3 control-карты
```

Слои не знают друг о друге больше необходимого: `measure` не знает, какой
бэкенд дал маску, `embed` не знает, откуда взялись обмеры. Сшивает всё
`arcbody/pipeline.py` — единственное место, где известна вся история.

## 3. Ключевые узлы

### 3.1 Perception — два бэкенда

| | `yolo` (боевой) | `classic` (запасной) |
|---|---|---|
| Модели | YOLOv8n-pose + YOLOv8n-seg | нет |
| Требует | `arcbody[yolo]`, веса | ничего сверх numpy/scipy |
| Фон | любой | однотонный, контрастный к одежде |
| Детерминизм | нет | полный |

`auto` предпочитает YOLO и молча откатывается на классический; явный `yolo`
никогда не откатывается — если его попросили и он не может, это ошибка
конфигурации, а не повод тихо ухудшить каждое измерение.

Классический бэкенд — не заглушка: это силуэтная фотограмметрия, которой
пользовались до нейросетей. Ключевые точки *выводятся*, а не детектируются:
антропометрическая пропорция задаёт полосу поиска, а конкретную строку внутри
неё находит сама структура силуэта (локальный минимум ширины для талии,
резкое расширение под шеей для плеча). Все выведенные точки получают
уверенность строго ниже единицы, чтобы дальше по конвейеру их можно было
отличить от настоящей детекции.

### 3.2 Measure — почему пропорции первичны

Одна фотография определяет *форму* тела и не определяет его *размер*. Поэтому:

- всё измеряемое выражено в долях роста;
- сантиметры появляются последним шагом, умножением на присланный рост;
- без роста сервис возвращает пропорции и прямо пишет, почему нет сантиметров.

Обхват никогда не измеряется — он реконструируется. Камера видит ширину
сечения, но не глубину. Сечение моделируется эллипсом; глубина берётся с
боковой фотографии, если она есть, и из популяционного априора, если её нет.
Два случая различаются полем `source` и заметно разной шириной интервала.

Априорные отношения глубины к ширине лежат одной видимой таблицей в
`arcbody/measure/schema.py`, а не размазаны по оценщику, потому что это
крупнейший источник ошибки одноракурсного обхвата и его придётся
перекалибровать.

### 3.3 Embed — ArcBody-энкодер

```
кроп 4×256×128 (RGB + силуэт)
   │
   ├─ BodyBackbone: стем + 4 residual-стадии (64/128/256/384)
   │    последняя стадия со stride 1 — приём из person re-ID: перепад
   │    «талия→бёдра» живёт в пространственном разрешении
   │
   ├─ pooling: avg ⊕ max
   │
   ├─ embedding (256) ──── L2 ──▶ выдача наружу
   │        │
   │        └─ BNNeck ──▶ ArcMarginProduct ──▶ логиты (только обучение)
   │
   └─ shape head ──▶ 14 безразмерных пропорций
```

Четвёртый канал — силуэт. Это самый дешёвый способ сделать эмбеддинг про
*форму*, а не про одежду: сеть получает контур готовым вместо того, чтобы
учиться сегментировать прежде, чем сравнивать.

Голова пропорций — не украшение. Она даёт второй, независимый путь к тем же
величинам, что считает геометрия. Когда пути расходятся сильнее чем на 25 %,
ответ содержит предупреждение; ничего не переопределяется молча.

Кроп привязан к росту, а не к рамке детекции. Рамка расширяется вместе с
разведёнными руками, и привязка к ней заставила бы сеть учиться отменять
изменение масштаба, не несущее информации о том, чьё это тело.

### 3.4 Gallery

SQLite + brute-force косинус по матрице в памяти. При потолке в 100 тыс.
человек это 100 МБ float и единицы миллисекунд на запрос; приближённый индекс
добавил бы зависимость, шаг сборки и провал полноты — в обмен ни на что.

Регистрация накопительная: повторная съёмка добавляет профиль, а не заменяет
его, и подпись человека — слияние всех профилей.

Фотографии не хранятся. Хранятся вектор, пропорции и обмеры. Удаление —
физическое, а не флаг.

### 3.5 GenAI-слой

Три правила промпта: говорить только известное (величина с интервалом шире
порога выбрасывается, а не округляется), говорить пропорциями, а не только
числами, и никогда не описывать человека — только геометрию тела.

Словесные ярлыки («широкие плечи») калибруются по **распределению выходов
самого оценщика**, а не по учебной антропометрии: сервис меряет ширину плеч
чуть ниже акромиона и длину ноги от тазобедренного сустава, поэтому по
анатомическим перцентилям обычное тело выходило узкоплечим и коротконогим.
Таблица — `arcbody/measure/calibration.py`, перегенерируется
`scripts/calibrate_ratios.py`.

Control-карты рендерятся в одном кадре с кропом энкодера, поэтому скелет,
силуэт и нормализованное фото совмещаются попиксельно и стыкуются в
multi-ControlNet без работы со стороны клиента. Цвета конечностей — по
соглашению OpenPose: адаптеры позы обучались именно на них.

## 4. Данные и обучение

Публичных наборов «фотография + обмеры рулеткой» мало, и они обременены
лицензиями. Поэтому в репозитории лежит параметрический генератор силуэтов
(`arcbody/training/synthetic.py`), который даёт три вещи, недоступные
собранному датасету: точный ground truth (тело *задано* своими пропорциями),
управляемую идентичность (один вектор параметров под разными позами и
одеждой — по построению один человек) и управляемый шум.

Он **не** фотореалистичен. Обученная только на нём модель не перенесётся на
фотографии. Это подложка для проводки, регрессионных тестов и аудита точности
геометрического оценщика.

Точка подключения реального корпуса — `FolderBodyDataset`: каталог на человека,
опциональный `ratios.json` с любым подмножеством известных пропорций,
опциональные маски. Цикл обучения при этом не меняется.

### Функция потерь

Одной угловой маржи не хватило, и причина структурная, а не в баге: это
900-классовый классификатор, видящий каждого человека около четырёх раз за
эпоху, так что каждый центр класса получает четыре шага градиента за эпоху.
Вспомогательная голова пропорций при этом училась быстро — значит, признаки
тела в стволе есть, а проблема в сэмпловой эффективности головы.

Каноническое для person re-ID лечение — сложить identity-лосс с batch-hard
triplet по батчам вида P личностей × K снимков. Батч тогда даёт O(P·K²) прямых
сравнений вместо 48 целей классификации. BNNeck существует ровно для того,
чтобы эти два лосса ужились: triplet — по признакам до него, классификация —
по признакам после.

## 5. Развёртывание

Один контейнер: FastAPI + uvicorn, модели грузятся на старте, чтобы контейнер
не сообщал о готовности раньше времени. Состояние — один файл SQLite на томе.
Никаких брокеров, объектных хранилищ и трекеров экспериментов: сервис
синхронный, состояние помещается в файл, а обучение — офлайн-задача с
артефактом-чекпоинтом.

## 6. Что осталось незакрытым

1. Точность на реальных фотографиях не измерена — вся валидация синтетическая.
2. Детектор YOLO выполняется, но на фото не проверен.
3. Пакетные задания не переживают перезапуск.
4. Априоры глубины и сигмы неопределённости требуют калибровки на измеренных
   людях; до этого сантиметры — оценка, а не обмер.
